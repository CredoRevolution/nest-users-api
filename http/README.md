# HTTP-запросы к API

Запросы для встроенного HTTP Client в PhpStorm. Два вида файлов:

- **`playground.http`** — ручная работа: жмёшь по одному запросу и смотришь, что пришло.
  Регистрация, вход, профиль, список пользователей, кэш, аватарки.
- **`00`–`07`** — автотесты: запускаешь файл целиком и смотришь, всё ли зелёное.

## Быстрый старт

1. `docker compose up -d` — Postgres, Redis и MinIO
2. Один раз создай бакет `avatars` в консоли MinIO: http://localhost:9001
3. `npm run start:dev`
4. Открой `.http` файл и выбери окружение **dev** в правом верхнем углу редактора

## Playground — ручная проверка

Все запросы в файле идут от «текущего пользователя» — того, кто последним
выполнил вход, регистрацию или refresh. Токены, `user_id` и `user_login` скрипт
`scripts/save-session.js` кладёт в переменные сам, копировать ничего не нужно.

Первый запуск на чистой базе:

1. «Регистрация dev_sasha» и «Регистрация dev_violetta»
2. Дальше — «Вход dev_sasha» или «Вход dev_violetta», чтобы переключаться между ними

Для экспериментов, после которых пользователя уже не вернуть (удаление, смена
пароля), есть «Новый случайный пользователь».

### Как проверять кэш

`GET /users` и `GET /users/:id` кэшируются в Redis на 30 секунд. В ответе есть
заголовок `X-Cache`, скрипт `scripts/show-cache.js` пишет его во вкладку
**Response Handler**:

| X-Cache | Значит |
|---|---|
| `MISS` | Ключа не было, ответ собран заново и положен в Redis |
| `HIT` | Ответ отдан из Redis, до контроллера и базы запрос не дошёл |
| нет заголовка | Роут не кэшируется |

Сброс кэша по id:

1. «Пользователь по id» → `MISS`
2. Ещё раз → `HIT`
3. «Поменять about»
4. «Пользователь по id» → `MISS` и новый about

Устаревший список:

1. «Найти себя в списке» → `MISS`
2. «Поменять about»
3. «Найти себя в списке» → `HIT` и **старый** about
4. Подожди 30 секунд, повтори → `MISS` и новый about

Что лежит в Redis, можно посмотреть руками — команды есть в конце `playground.http`.

## Автотесты

| Файл | Что проверяет | Нужен MinIO |
|---|---|---|
| `00-smoke.http` | Счастливый путь: регистрация → профиль → refresh → ротация | |
| `01-auth.http` | Регистрация, вход, refresh, защита от повторного refresh, валидация | |
| `02-profile.http` | `/profile/my`, JwtAuthGuard, обновление, смена пароля, мягкое удаление | |
| `03-users.http` | `GET /users`: пагинация, поиск, экранирование LIKE. `GET /users/:id` | |
| `04-users-active.http` | `GET /users/active`: кто считается активным и когда перестаёт | да |
| `05-avatars-upload.http` | Загрузка: форматы по содержимому, кривой multipart, лимиты | да |
| `06-avatars-delete.http` | Удаление: своя, чужая, кривой id, место в лимите | да |
| `07-cache.http` | `X-Cache` HIT/MISS, сброс после PATCH и DELETE, что не кэшируется | |

Запуск — кнопка **Run all requests in file** в шапке файла. Результаты во
вкладке **Tests**.

Каждый файл самодостаточный: сам регистрирует пользователей с уникальными
логинами (`auth_<время>`, `usr<время>_a` и так далее), поэтому файлы можно
запускать в любом порядке и сколько угодно раз. Глобальные переменные у каждого
файла со своим префиксом (`auth_`, `prof_`, `users_`, `act_`, `upload_`, `del_`,
`cache_`) и не пересекаются.

`07-cache.http` проверяет HIT, поэтому запускай его целиком: весь файл должен
уложиться в 30 секунд TTL. По одному запросу с паузами он начнёт краснеть.

Для теста на 413 в `05-avatars-upload.http` нужен файл, которого нет в git.
Создай его один раз в Git Bash:

```bash
head -c 11M /dev/urandom > http/fixtures/big.jpg
```

### Все автотесты из терминала

Через CLI-версию HTTP Client в Docker, приложение запущено на 3000:

```powershell
docker run --rm -v "${PWD}/http:/workdir" jetbrains/intellij-http-client `
  --env-file http-client.env.json --env dev `
  -V baseUrl=http://host.docker.internal:3000 `
  00-smoke.http 01-auth.http 02-profile.http 03-users.http `
  04-users-active.http 05-avatars-upload.http 06-avatars-delete.http 07-cache.http
```

## Как устроены файлы

- `### Название` — начало запроса, название видно в списке запусков
- `< {% ... %}` — скрипт **до** запроса. Здесь генерируются уникальные логины:
  `request.variables.set(...)` — для этого запроса, `client.global.set(...)` — для следующих.
  У таких запросов название продублировано в `# @name`, иначе HTTP Client его теряет
- `> {% ... %}` — скрипт **после** ответа. `client.test(...)` — именованная проверка
- `> scripts/файл.js` — тот же скрипт после ответа, но из отдельного файла

## Окружение

`http-client.env.json` коммитится, секретов там нет. Для приватных значений
создай рядом `http-client.private.env.json` — он в `.gitignore` и перекрывает
значения из основного файла.

Swagger со всеми роутами: http://localhost:3000/docs
